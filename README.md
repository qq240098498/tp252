# 冷链温控与批次放行台

冷库与冷藏车的温控值班台：录冷库与探头、登批次、盯温度记录、算超限与断链、判放行还是拒收。

## 运行

```
npm install
npm start
```

默认端口 5252（`PORT` 可以覆盖），数据存在 `data/db.json`，页面在 `/`。

## 页面

- **概览**：冷库与运行中数量、探头数量与已过校准期的探头数、批次总数与各状态条数、温度记录条数与人工记录数、放行与拒收条数、当前满足放行条件的批次数与被挡下的批次数、没有任何温度记录的批次数、最高与平均 MKT、按冷库一行给出探头与批次数。
- **冷库与探头**：冷库台账（编码、名称、类型、位置、库位、状态）与探头台账（编号、所属冷库、位置、状态、校准有效期、记录条数），都带增改删。
- **批次**：批次清单（批次号、品名、规格、件数、所在冷库、入库时刻、状态、温度记录条数、最长超限、累计超限、MKT、断链数、变更次数、放行情况），行内展开：
  - **变更履历**：登记批次中途换库位/换车厢/换设备，每条记从哪到哪、变更时刻、原因、经办人、登记时刻，以及是判定前登记还是放行后补登；
  - **分段归属与每段统计**：每次变更把批次切成一段，逐段给出冷库/车厢、设备、记录条数、最长超限、累计超限、段内断链、MKT；温度记录逐条标注归属段；段与段交接处的大缺口单列为「换链缺口」，不计断链；
  - **判定口径对照**：从「登记前旧口径」到「每次变更后」逐步列出记录数、各项判定值与放行结论，标出哪一项变了、结论是否翻转，并归因到具体那次变更；
  - 超限段、断链缺口（整批口径参考）、放行判定四项与放行单，并提供「登记变更」「放行」「拒收」入口。
- **温度记录**：记录清单（批次、探头、时刻、归属段、温度、来源、登记人、是否超限），支持按批次与探头筛选、单条新增与删除。
- **放行台账**：放行与拒收记录（批次、决定、时刻、经办人、当时的 MKT、最长超限、累计超限、断链数、**判定时用的是几段/前几次变更的口径**、依据）。放行之后又补登记过变更的，台账上明确标注「放行后又登记 N 次变更，本单结论不重算」。

## 口径（页面上的说明与数字都要与本段一致）

1. **温度带**：默认 2 到 8 摄氏度（可在设置里改），低于下限或高于上限都算超限。
2. **超限段**：按时刻顺序逐条判，连续超限的时段算一段，**中间只要有记录回到范围内就断开**；每段的时长按该段相邻记录的实际时刻差累加。
3. **累计超限**：一个批次从入库到当前，所有超限段的时长之和；**跨月不重置**，按批次周期累计。
4. **断链**：相邻两条记录的时刻差超过 `chainGapMinutes`（默认 15 分钟）算一处断链，缺口时长按实际时刻差算。**只在同一段（同一库位/设备归属期）内判断链**；段与段交接处的缺口是拆装、搬运造成的，单列为「换链缺口」，不计断链。
5. **MKT（平均动力学温度）**：按动力学公式算，写成 `MKT = −Ea / (R × ln((Σ e^(−Ea/(R·T)) ) / n)) − 273.15`（活化能 Ea 取 83144 J/mol、气体常数 R 取 8.314，T 用开尔文，n 为参与计算的记录条数）；**不是把温度取平均**。
6. **放行判定四条**：单次连续超限不超过 `allowExcursionMinutes`（默认 30 分钟）、累计超限不超过 `allowTotalExcursionMinutes`（默认 120 分钟）、全程没有断链、**参与判定的探头都在校准有效期内**。四条同时满足才算满足放行条件；**没有任何温度记录的批次不能放行**。
7. **同一探头同一时刻既有自动记录又有手工更正记录时，以手工记录为准**；停用探头名下的记录不参与判定。
8. **停用与检修中的冷库**：其批次仍然照常记录与判定，但在清单里要标出来。
9. **设备与库位变更（换库/换车厢/换探头）必须登记，不能直接改批次归属**。一条变更记录：变更时刻、从哪个冷库/车厢与探头、到哪个、原因、经办人、登记时刻。
   - **边界口径**：变更时刻**整刻起**的记录计入新段——例如 08:00 装车，08:00 的那条记录算新车上的；08:00 之前（不含整刻）算旧段。变更只能按时间顺序补登（新登记的时刻要晚于上一条）。
   - **分段统计**：每次变更开一段，各段独立统计记录条数、最长/累计超限、段内断链与 MKT；「最长超限」取各段最长者，「累计超限」为各段之和，断链只数段内的。
   - **对照**：每登记一次变更都给出与登记前口径的对照（记录数、各判定项数值、满足与否），标明哪几项变了、放行结论是否翻转、是哪次变更导致的。
   - **放行冻结**：放行/拒收的那一刻，把当时用的分段口径（前几次变更、几段、每段的库位/设备/记录数/超限/断链）冻结进放行单。之后再补登记变更，只影响今后的统计与判定，**过去的放行结论不按新归属重新解释**；已放行批次允许补登变更，页面上标出「放行后补登」，台账上标出放行单口径与之后变更次数。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/health、/api/summary、/api/settings | 健康检查、概览、设置（PATCH 可改） |
| GET / POST | /api/rooms | 冷库清单（支持 status、type、keyword）/ 新增 |
| GET / PATCH / DELETE | /api/rooms/:id | 详情（含探头与批次）/ 修改 / 删除 |
| GET / POST | /api/probes | 探头清单（支持 roomId、status）/ 新增 |
| PATCH / DELETE | /api/probes/:id | 修改 / 删除 |
| GET / POST | /api/batches | 批次清单（支持 roomId、status、product）/ 新增 |
| GET / PATCH / DELETE | /api/batches/:id | 详情（含记录与归属段、分段统计、换链缺口、变更履历、逐步口径对照、放行单）/ 修改（不能直接改 roomId/probeId，要走变更登记）/ 删除 |
| GET / POST | /api/batches/:id/changes | 变更履历清单 / 登记一条库位/设备变更，body `{toRoomId,toProbeId,changedAt,reason,operator,remark}`（探头传 `__keep` 表示随货沿用），返回登记前后判定对照 `{change,batch,before,after,diff,releasedBasis,comparison}` |
| GET | /api/batches/:id/release-check | 这个批次当前口径的放行判定；可加 `?k=0` 只按前 k 次变更评估（k=0 为登记前旧口径） |
| POST | /api/batches/:id/decision | 放行或者拒收，body `{decision, decider, decidedAt, basis, remark}`；放行单冻结当时的分段口径（`changeCount`、`stints[]`、`pass`、`boundaryRule`） |
| GET / POST | /api/records | 温度记录（支持 batchId、probeId、source、from、to）/ 新增 |
| DELETE | /api/records/:id | 删除一条记录 |
| GET | /api/releases | 放行台账（支持 batchId、decision） |

出错的返回统一是 `{"error":{"code":"...","message":"...","details":{...}}}`，`details` 里会点名是哪个字段没过。
